## 2. P0 级（会污染学习数据/统计，建议优先修）

### P0-1 答案修订后不回刷历史判分（已实证，影响 FSRS 与掌握度）

q687/q691 的日志时间线与管理员改答案的时刻精确重合：

| 时间 | 事件 |
|---|---|
| 05-17 10:21:42 | 用户对 q687 提交「答案错误」反馈 |
| 05-17 10:21:55 | 答 `B` 判**对**（当时答案键还不是 ["B","D"]）|
| 05-18 11:19:51 | 再答 `B` 仍判**对** |
| 05-18 12:13:59 | q691 答 `["A","D"]` 判**错**（此时 q691 答案键已改为 ["A","D"]，但判分路径未同步？）|
| 05-22 07:12:01 | q691 答 `["A","D"]` 仍判**错** |
| 05-22 07:24:16 起 | 同一答案 `["A","D"]` 开始判**对** |

- 全库严格复核（把答案折算成字母集合重算）：**11 条日志与当前答案不一致**（single 3、multi 8），全部落在 2026-05-16～05-31 的答案修订窗口内。
- 代码侧确认：当前 `origin/main`（f5f74aa）的多选判分是等长集合比较（`use-practice-controller.tsx:262`），**判分函数本身没有缺陷**；问题在于**改答案不回溯**：全仓无 regrade 逻辑（grep `regrade|recompute|回刷` 无命中）。
- 影响：这 11 条日志已进入 SRS 与 user_mastery，而且同一批被修订的题（687/691/1588/1894/1915/1920）还有更多历史记录未复核。

**建议**：`questions.answer` 更新时，在同一事务里对该题全部 practice_logs 重算 `is_correct`（用当前判分函数），并把受影响用户的 `question_srs` 对应卡重置状态（或标记 stale 下次复习重排）；`user_mastery` 按 tag 重算。改动只需一个 service（admin 改题入口单点）。

### P0-2 外部 Agent API 的答题记录服务端不复核，且无来源标记

- `import-service.ts:270`：*「对错由调用方 agent 判定，服务端不重算」*；`external.ts:912` 同上。
- 库里可见后果：**339 条日志没有 session_id**、其中大量 `duration_ms=0`、**348 条 user_answer 为空但全部 is_correct=0**——这些不是网页作答产生的，是外部写入路径；它们同样写进了 SRS（判错→Again）。
- 没有 `origin`/`source` 字段，事后无法区分「用户真答错」与「导入/agent 上报」。

**建议**：practice_logs 加 `origin`（web|agent|import）；导入路径的日志**不触发 SRS**（或单独标记不排期）；server 端至少做「答案位数/格式合法性」校验，拒绝空答案落库为「判错」。

### P0-3 空答案=判错直接进 SRS

- 348 条空答案日志全部 `is_correct=0`，涉及 single 190 / multi 106 / truefalse 44 / fill_blank 8。
- 44 条判断题空答案尤其可疑：判断题在 UI 上必须点 A/B，空答案说明提交路径有洞（跳过按钮？未作答提交？）。
- 若为「跳过」，应记录 `skipped` 而非 `wrong`——现在等于把用户的「没做」当「做错」排进复习。

**建议**：区分 `is_correct` 与 `status`（answered/skipped），跳过的题不进 SRS。

### P0-4 REST 提交路径的多选判分缺分支（随 P0-1 修复一并补齐）

- `submitAnswerWithValidation`（REST 路由 / 移动端）调用的是**没有多选分支**的判分函数：
  只有「字符串完全相等」或「单字母↔选项文本映射」能命中——选项顺序不同
  （`["D","B"]` vs `["B","D"]`）即误判。
- 网页端走客户端判分（`use-practice-controller.tsx` 内含等长集合比较），所以问题只在
  REST 路径暴露；快照里多选日志集中在 review 模式，与此路径吻合。
- 修复：判分抽出为 `answer-check.ts` 并补齐多选集合比较（分支 `fix/regrade-on-answer-update`）。

## 3. P1 级（数据质量与体验）

### P1-1 重复题 163 道（81 组），其中 **30 组答案互相冲突**

- 来源分布：source=NULL 160 道（早期种子/手工）、pdf_import 337 道为主力来源、fenbi_import 20 道。
- 影响：38 道重复题有练习记录、37 道有 SRS 行——同一题的历史被拆到两个副本，统计与排期碎片化。
- 更危险的是 60 道「同题干不同答案」——两个副本至少一个是错的，而用户做题时随机撞见哪一个全凭运气。

**建议**：导入时以「归一化题干哈希」做内容级去重（当前只按 external_id 去重，NULL 时全放过）；对 60 道冲突题人工裁决，保留一份并迁移日志/SRS（`UPDATE practice_logs SET question_id=...`）。

### P1-2 84 道 type=NULL 的兜底题混入正式题库

- id 5–88，创建于 2025-12-22，source=NULL，type=NULL；`questions` 读取时 `type || "single"` 兜底（practice.ts:270）。
- **22 条练习记录（用户 19）+ 20 条 SRS**——用户在正常刷题流里做到了它们，它们也计入掌握度。
- 无任何标记可把它们从统计中剔除。

**建议**：`source='fallback'`、补 `type`；推荐/统计/掌握度查询排除 fallback；或直接移出题库。

### P1-3 SRS 积压无上限

- 2473 张已到期（用户 1：1993；用户 19：480）。快照前最后活动是 8 月底，积压已 2.5 个月。
- 用户下次打开将面对约 2000 张的「今日复习」——按每天 100 张要 20 天清完，几乎必然弃用。

**建议**：到期队列单日上限（如 50–100），超出顺延；提供「积压过大时整体延后 7 天」的批量操作（与回忆自测规格 §3 同一规则）。

### P1-4 会话台账不完整，分析与时长统计不可信

- `practice_sessions` **没有 ended_at / completed 字段**：无法区分「做完」和「做一半退出」。
- 14 个会话 `total_questions` 与实际日志数不符；7 个会话零日志。
- `review_count` 全库恒 0（字段未接线）；`total_duration_ms` 之和 8.8 h，与 4990 条日志的 duration 需要重建才能对齐。
- 后果：`analysis_report`（16 个非空）与任何基于会话的报表都可能失真。

**建议**：加 `ended_at/completed`，完成时回写；`review_count` 要么接线要么删掉；用日志重建会话统计（一次性回填脚本）。

## 6. 复跑 SQL（对快照只读执行）

```sql
-- 判分不一致（多选，严格集合比较）
SELECT l.id, l.user_answer, q.answer
FROM practice_logs l JOIN questions q ON q.id=l.question_id
WHERE q.type='multi' AND l.user_answer IS NOT NULL AND trim(l.user_answer)<>''
  AND lower(replace(l.user_answer,' ','')) <> lower(replace(q.answer,' ',''));
-- 重复题与答案冲突
SELECT content, count(*) c, count(DISTINCT answer) da FROM questions GROUP BY content HAVING c>1;
-- 空答案/无会话日志
SELECT count(*) FROM practice_logs WHERE user_answer IS NULL OR trim(user_answer)='';
SELECT count(*) FROM practice_logs WHERE session_id IS NULL;
-- SRS 积压
SELECT user_id, count(*) FROM question_srs WHERE due_date < datetime('now') GROUP BY user_id;
```
