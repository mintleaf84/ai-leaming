## 2026-11-13 · 回忆自测 P1（数据层 + 卡组导入导出）

规格：`fj-teacher-exam-physics/docs/ai-learning-recall-spec.md`。以下是规格未定点按默认值自定的部分。

| 决策                      | 选择                                                                                                                                                                                    | 理由                                                                                                                       | 备选/代价                                                                  |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 多用户边界                | `recall_card_states` / `recall_review_logs` 带 `user_id`（FK cascade）；卡组与卡片内容**全局共享**不加 `user_id`；`recall_decks.owner_user_id` 可空（NULL=公共卡组）                    | 内容与源码解耦、靠文件分发，进度是私有的；两种数据混在一张表会把"共享内容"变成"谁先导入谁所有"                             | 卡组也按用户隔离：同一份文件会被 N 个用户各导入一份，纠正一处错卡要改 N 次 |
| 文件导入的卡组归属        | 新建时 `owner_user_id = NULL`（公共）                                                                                                                                                   | 否则第二个用户导入同一份共享卡组文件会被归属校验挡住                                                                       | 记成导入者所有：与他人分享文件时直接报错                                   |
| 两张内容/进度表的连接方式 | 卡片内容（prompt/items/blanks）只在 `recall_cards`，进度只在 `recall_card_states`，accept 覆盖内容时**根本不写 state 表**                                                               | "改内容不丢进度"不是靠小心操作，而是数据模型上就没法一起写坏                                                               | 内容与状态同表：一次 UPDATE 就可能把 due 冲掉                              |
| Learning steps            | 关闭（`generatorParameters({ enable_short_term: false })`）                                                                                                                             | 队列是每日粒度，1m/10m 学习步当天永远消费不到，只会把卡反复拉回当天                                                        | 开着：新卡首评后 due 仍是当天，用户刷不到任何变化                          |
| FSRS 参数来源             | 抽到 `src/lib/srs/fsrs-config.ts`（`FSRS_REQUEST_RETENTION = 0.9` + `createRecallScheduler()` / `createQuestionScheduler()`），`services/srs.ts` 改为从该文件取参数但**实例仍各自持有** | 参数只能有一份；实例内部有可变状态（seed 等），跨模块共享同一实例会互相污染                                                | 两个模块各写 `0.9`：改保留率时必然漏一处                                   |
| 重测卡评分推导            | `mode="retest"` 时：`pendingItems` 全对 → `Good`；仍有错 → `Hard`；点「全没想起」→ `Again`。首发与重测同一套推导，只是输入条目集不同                                                    | 评分只看"这次呈现的条目判得怎么样"，重测呈现的就是上次错的，不该因为"上次错过"再扣一档                                     | 重测单独一套阈值：多一组无人能解释的魔法数字                               |
| 条目匹配器                | 保持规格的「`keywords` 任一命中」，但日志加 `keyword_hits` / `keyword_total`（P1 只建列，不写不读）                                                                                     | 规则可能过松/过严，先留痕；没有这两个数，事后只能用用户改判反推                                                            | 立刻上加权匹配：在没有真实数据时等于凭空调参                               |
| 拼音/繁简                 | P1 **不引入** `pinyin-pro` / `opencc-js`：归一化只做去首尾/连续空白、去中英文标点、全角转半角；`verbatim` 卡也只走同一套                                                                | 拼音容错针对的是"真实错别字反馈"，现在一条都没有；先上两个大依赖等于给自己加维护面                                         | 现在就上：多两个含大词典的包，且没有基准集可验证效果                       |
| 切日边界                  | `Asia/Shanghai 04:00`，工具 `src/lib/recall/study-day.ts`（`getStudyDay` / `getStudyDayStart`）                                                                                         | 23:30 打开应用的人不该在几分钟后被算成"新的一天"，补做上限与今日计数会瞬间重置                                             | 自然日 00:00：夜里学习的人每天被切两半                                     |
| 未知 `schema` 版本        | 直接拒绝导入并给出可读错误（不做兼容猜测）                                                                                                                                              | 猜测会把不认识的字段静默写坏；卡组文件是外接数据，出错必须由内容侧修                                                       | 尽力解析：坏数据进库后无法回溯                                             |
| 分组（`groups`）存储      | `recall_decks.groups_json` 存整棵树（**没有**单独建表，规格也没列这张表）                                                                                                               | 不存就丢掉分组标题与顺序，`exportDeck` 就不再与导入同格式（规格 §1.1 的硬要求）                                            | 只留 `card.group_key`：导出后 47 节点树退化成裸 ID                         |
| 导出缺组时的兜底          | 卡片引用了未登记分组 → 导出补一条 `title=groupId` 的占位分组                                                                                                                            | 宁可标题退化，也不能导出一个自身校验不过的文件                                                                             | 直接报错：用户没法导出，也不知道该改哪                                     |
| 冲突默认策略              | `keep`（保留库内内容），冲突逐卡回报；**keep 时不更新 `prompt_hash`**                                                                                                                   | 用户没点"采用新文件"之前，冲突必须每次导入都继续可见；改了 hash 下次就被当"内容一致"静默跳过                               | 更新 hash：冲突只报一次，之后永久静默                                      |
| 文件里没有的卡            | 不删除，只回 `missingInFile`                                                                                                                                                            | 删卡会连带删掉该用户全部进度；UI 提示后由用户决定                                                                          | 自动删：一次导错文件就抹掉进度                                             |
| 并发                      | 复用 `import-service` 导出的 `withImportLock`（全站唯一的写导入锁）                                                                                                                     | 两条导入链路共用同一条 SQLite 连接，各持一把锁无法互斥：「粉笔导入事务进行中 + 回忆导入开始」照样撞 statements-in-progress | 各持一把锁：看似隔离，实际只在单链路内有效                                 |
| 迁移写法                  | 手写 `0012_recall_self_test.sql`（`CREATE TABLE/INDEX IF NOT EXISTS` + 更新 `_journal.json`）                                                                                           | 与 0009–0011 一致；`meta/` 快照只到 0008，`drizzle-kit generate` 会从旧快照重新 diff 出重复列                              | `drizzle-kit generate`：会生成一堆已存在列的 ADD COLUMN                    |
| 测试夹具                  | 4 张 recall 表登记进 `MIGRATION_ONLY_TABLES`，**不**进内存夹具                                                                                                                          | 导入导出是真实写库逻辑，测试必须跑真实迁移（与 `import-idempotency` 同做法）                                               | 补进夹具：多一份手写 DDL 要跟着迁移漂移                                    |

## 2026-11-13 · Agent API P1（鉴权地基）

| 决策              | 选择                                                                                                                                                      | 理由                                                                         | 备选/代价                                                       |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 全局 key 的身份   | `api_keys.user_id IS NULL` 视为**全局 key**，操作身份取 `API_GLOBAL_USER_ID`（缺省 `1`）                                                                  | 既有 key 全是"工具接入"性质，升级时不该强制绑用户；缺省 1 是种子里的站长账号 | 迁移时把 key 全部绑到 1：语义上把机器身份写成真人，后续无法区分 |
| 全局 key 的语义   | **只解决「是谁」，不解决「能做什么」**：它等价于站长身份，但**仍受 `scopes` 限制**（迁移后既有 key 默认 `read`，写接口会 403）。返回体带 `isGlobal: true` | 身份与权限分离，后面收紧只改 scope，不用再动身份模型                         | 让全局 key 绕过 scopes：一旦泄漏就是全站写权限，风险不可控      |
| 停用 key 的状态码 | 401（原实现是 403）                                                                                                                                       | 语义上"凭证不可用"就是未认证；403 留给"认证通过但作用域不足"，两个码不再混淆 | 保留 403：外部脚本已按 403 判停用会静默失效                     |
| 作用域模型        | `read` ⊂ `write` ⊂ `admin` 递进包含，存为单列文本                                                                                                         | 单列够用、SQL 可读；递进包含让"加权限"不必回填历史 key                       | 位掩码 / 关联表：为多角色组合预留，但本期无组合需求             |
| 审计范围          | 只记 `POST/PATCH/PUT/DELETE`，读请求不入库                                                                                                                | 读占绝大多数且无审计价值；审计表会被读流量淹没                               | 全量记录：写放大与清理成本都不可控                              |
| 审计失败          | 只 `logger.error`，不抛出、不阻断响应；写入放在 `after()` 里                                                                                              | 审计是旁路；写不进去不能把业务一起弄挂，也不能让 `busy_timeout` 拖慢响应     | 同步等待：写锁竞争时客户端要等审计落库                          |
| 审计挂载顺序      | 审计中间件在鉴权**之前**挂，但**只记能追溯到具体 key 的写请求**（403 记，401 匿名不记）                                                                   | 越权尝试要留痕；而完全匿名的 POST 不记，否则任何人刷请求就能把审计表灌满     | 401 也记：表无限增长且无法归因                                  |
| `last_used_at`    | `after()` 后台更新，非请求作用域退化为即时异步                                                                                                            | 不阻塞请求；单测直接调 `app.request` 时 `after()` 会抛，需该分支             | 直接 `await`：每请求多一次写                                    |
| 迁移写法          | 手写 `0011_*.sql`（`ADD COLUMN` / `CREATE TABLE IF NOT EXISTS`），不生成 drizzle snapshot                                                                 | 与 0009/0010 一致；快照缺失的既有状态不因本次改变                            | `drizzle-kit generate`：会从 0008 快照重新 diff，产出重复列     |

## 2026-11-13 · Agent API P3a（导入答题记录）

| 决策            | 选择                                                                 | 理由                                                                   | 放弃的方案                                           |
| --------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------- |
| 幂等键          | 请求体 `sessionKey` → `practice_sessions.source_key = "agent:<key>"` | 复用已有唯一约束与 `findExistingSession`，不用新建幂等表               | 单独 `idempotency_keys` 表：多一张表、多一次迁移     |
| `isCorrect`     | 由调用方（agent）判定并提交，服务端不重算                            | agent 有服务端没有的上下文（题干原文、对话）；重算会强加"练习模式"语义 | 用标准答案重算：导入场景下语义不对                   |
| 非法 questionId | 整批 400，只回前 5 个                                                | 静默跳过会让 agent 以为导入成功，统计对不上                            | 跳过并回 `skipped`：调用方难察觉                     |
| 校验顺序        | 幂等预检在事务外；题目存在性预检在**事务内第一步**                   | 校验与写入之间没有时间窗，预检失败整体回滚（三表 0 行）                | 事务外查题：查完到写入之间题目可能被删               |
| 会话快照        | `questions_json` 存**纯 id 数组**                                    | `getSessionById` 只对数字/字符串数组走 id 分支，对象数组会解析坏掉     | 存 `[{questionId}]`：字段更"自解释"但详情页直接崩    |
| 掌握度          | 与粉笔导入共用 `applyMasteryDeltas`                                  | 两条链路口径必须一致，否则同一批数据不同分数                           | 各写一份：短期快、长期漂移                           |
| SRS 同步        | 本期**不做**                                                         | 导入的是历史作答，不该立刻生成复习卡，且同步会引入 `SQLITE_BUSY` 窗口  | 导入后立即 `syncFromPracticeLogs`：语义混淆 + 锁竞争 |
| 批量上限        | 500 条/批，整批原子                                                  | 单事务可控；超限让调用方分批并在每批用不同 `sessionKey`                | 无限批量：一次长事务会卡住本地库                     |
